# OPS-01 — Fix broken pnpm pin and unblock Changesets release CI

## What was done

- Diagnosed the failing GitHub Actions workflow (`pnpm/action-setup@v6` step):
  `package.json` pinned `pnpm@11.13.0`, a broken release whose `@pnpm/exe`
  build shipped without a binary. The action's self-installer refuses it with
  `ERR_PNPM_BROKEN_PNPM_RELEASE`.
- Bumped the `packageManager` field to `pnpm@11.20.0` (latest stable).
- Fixed `ERR_PNPM_OUTDATED_LOCKFILE` from the `chore: up deps` commit: the
  committed `pnpm-lock.yaml` was internally corrupted — the `packages/eslint`
  importer pinned `eslint` specifier `^10.2.0` to resolved version `9.39.4`
  (doesn't satisfy the range). The stale local `node_modules` (with the old
  `eslint@9.39.4`) poisoned every `pnpm install` attempt, which kept saying
  "Already up to date" even with `--force`/`--fix-lockfile`.
- Regenerated the lockfile from scratch (removed `node_modules` + lockfile,
  then a fresh `pnpm install --lockfile-only`); the stale tree now resolves
  `eslint@10.8.0`.
- Fixed the next CI failure (`@tala-tools/tsdown:build`):
  `rolldown-plugin-dts@0.23.2` crashed with `Cannot read properties of
  undefined (reading 'useCaseSensitiveFileNames')` because the regenerated
  lockfile linked it to the root's `typescript@7.0.2`, whose native API no
  longer exposes `ts.sys`. The corrupted old lockfile had accidentally linked
  it to an auto-installed `typescript@6.0.3`, which is why builds passed
  before.
- Pinned `"typescript": "6.0.3"` as an exact devDependency of
  `@tala-tools/tsdown`, deterministically restoring the `typescript@6.0.3`
  link for `tsdown@0.21.7` / `rolldown-plugin-dts@0.23.2` regardless of pnpm
  version.
- Rejected bumping the tsdown peer to `0.22.14`: its
  `rolldown-plugin-dts@0.27.14` supports TypeScript 7, but requires
  `node ^22.18.0 || >=24.11.0`, which violates the repo's Node `>=20.19.0`
  constraint. `tsdown@0.21.10` still bundles the TS7-incompatible plugin
  family, so pinning TS 6.0.3 is the only Node-20-compatible option.
- Verified the fix by reproducing CI locally: a fresh `git worktree` at HEAD
  fails with the exact CI error, then passes `pnpm install --frozen-lockfile`
  and `pnpm --filter @tala-tools/tsdown build` once the regenerated lockfile
  and the tsdown devDependency change are in place. Full `turbo run build`
  passes (3 tasks) and typecheck passes.

## Key decisions

- Keep the fix minimal: one-line `packageManager` bump, no workflow changes.
  The `pnpm/action-setup@v6` self-installer picks the version up from the
  manifest automatically.
- Regenerate the lockfile rather than hand-editing the broken importer entry.
  The old lockfile also carried duplicate stale resolutions (eslint 9.39.4 +
  10.7.0 + 10.8.0, oxlint 1.75.0 + 1.77.0), so a full re-resolution was the
  only consistent fix.
- The remaining peer warnings (`typescript-eslint`/React plugin ranges vs
  TypeScript 7 and ESLint 10) are pre-existing and documented in AGENT.md.
- Keep `@tala-tools/tsdown` on peer `tsdown@0.21.7` + devDep
  `typescript@6.0.3`; do not raise to `tsdown@0.22.14` because of its Node
  `>=22.18` engine requirement. No changeset adjustment needed: the new
  typescript entry is a devDependency only, so the queued patch release for
  `@tala-tools/tsdown` still matches.

## Next steps

- Push the fix and re-run the release workflow so the Changesets versioning
  pull request (currently queued: patch for `@tala-tools/eslint` and
  `@tala-tools/tsdown` via `fancy-months-yawn.md`) can be created and merged.
- The devDependency typescript pin in `packages/tsdown` should be revisited
  once `tsdown@0.22.x` (or `rolldown-plugin-dts` v0.27+) relaxes its Node
  engine requirement so the package can move to TypeScript 7.
